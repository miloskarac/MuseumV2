# Phase 7.1 — Save compatibility baseline

Verified on 2026-11-08 against the working tree containing the Phase 6 batch-1 fixes. This task adds tests, synthetic fixtures and this document only. No gameplay, schema, prices, browser storage or production code changed; no Phase 7 expansion or credit migration is implemented.

## Contract and fixture provenance

Readers chain through schemas 20 (deposits), 19 (upgrades), 18 (custody), 17 (helpers), 16 (tickets), 15 (travel), 14 (museum purchases), 13 (economy), and the historical V2 journey reader for 1–12. These are V2 versions, not V1-game save import.

`tests/save-compatibility.test.ts` follows the existing `node:test` / strict assertion convention. Existing tests use local fixture factories, deterministic seeds, JSON round trips and in-memory `StoragePort` adapters; there was no shared fixture utility to extend. The new JSON corpus freezes concrete inputs so future content/constructor changes cannot silently regenerate both the input and expectation.

`tests/fixtures/save-compatibility.json` contains nine named, independent snapshots. All are synthetic, with economy seed 42; none came from player storage. They were prepared once using existing constructors, transitions, purchases, ticket sales and explicit synthetic journey/custody snapshots, then checked by the applicable readers. This is validator-valid test data, not a recording of a complete browser playthrough. Do not regenerate these fixtures simply to make a later migration pass.

## Tests and invariants

The new suite adds **45 tests**:

- Exact schema-21 parsing and repeated load/serialize/load cycles for all five current fixtures, using a different new-session seed to detect manifest replacement.
- Fixed numerical expectations for money, pending cash, receipts, deposits, ticket counters, collection/placement and site closure. Completed and partial assembly remain distinct from collection and excavation closure.
- Original-site delivery recovery, interrupted cleaning, paid helper/upgrades and no automatic collection. Load retires paid visitors but retains unpaid visitors, counters and pending income; it settles delivery custody into storage without granting fossil inventory.
- Replaying retained soil progress pays no additional rewards. Repeated purchases, placement, ticket payment for a retired visitor and cash collection do not duplicate their effects.
- Four historical migrations retain progress and financial records, add no collectible historical ticket income, and remain stable after serialization. Pre-economy progress receives no retroactive soil coins; legacy ownership keeps zero-paid provenance.
- Failed west-wing completion through both remainder purchase and final one-coin contribution: durable storage retains the old deposit until retry; retry publishes once, clears only the wing deposit and records the full 18-coin receipt. This uses the real `createCommitter` and an in-memory failing storage adapter.
- 27 corrupt-state cases plus malformed/future-schema/unavailable-storage handling. Cases include inconsistent balances, pending cash without sales, invalid/mixed/duplicate receipts, owned-plus-partial contradictions, premature closure, inconsistent collection/placement, invalid soil claims, ticket history, helper payment, custody and upgrades. The loader must return `invalid`/`unavailable`, never silently start over. Read-only adapters fail on any attempted write/delete.

The current financial invariant can be expressed as:

`coins + pending tickets + paid museum receipts + site receipts + helper receipts + upgrade receipts + partial deposits = 20 starting coins + claimed soil rewards + lifetime ticket income`

Legacy receipts contribute zero. Partial deposits have already reduced spendable coins; completing a purchase replaces the deposit with a receipt for the entire original price, not just the last payment. Load must preserve that distinction.

## Future west-wing expansion credit

Approved direction from the Phase 7.1 task: money spent on the old west wing must become credit toward a future museum expansion. The following is migration guidance, not implemented behavior or approval of new prices/ownership rules.

| Existing state | Authoritative persisted field | Credit basis |
| --- | --- | --- |
| Purchased wing | `museum.owned` entry `{ id: 'west-wing', source: 'purchase', paid: 18 }` | Validated receipt's `paid` amount, currently 18. |
| Partially paid wing | `payments.partial['west-wing']` | Validated positive integer, currently 1–17; ownership has not been granted. |
| Legacy wing | `museum.owned` entry `{ id: 'west-wing', source: 'legacy', paid: 0 }` | Zero monetary credit. Existing access is a separate entitlement, not evidence of spending. |
| No receipt/deposit | Neither field | Zero credit; no inferred purchase. |

`buyPurchase` removes a partial entry and writes the full-price receipt atomically. `parsePaymentSave` rejects deposits on owned offers and full-price deposits without a receipt. `parseMuseumSave` rejects duplicate receipts and partially legacy/mixed halls; legacy migration currently grants all old museum offers together. Schema 19 and earlier have no partial-payment field.

Recommended future migration:

1. Validate the untouched source against frozen historical definitions before changing identifiers, costs or prerequisites. Determine the credit from the valid paid receipt **or** partial deposit; never add both, estimate from lifetime earnings, or infer payment from ownership alone. Reject contradictory records rather than selecting a favorable interpretation.
2. Convert that paid value into one explicitly versioned expansion-credit record, with stable source/provenance and consumed/remaining accounting. Mark the old liability as converted in the same durable snapshot. If retaining an old receipt for audit, exclude it from the new accounting total to prevent double counting. A second migration of the same input must produce the same result; a load of the new schema must not regrant credit.
3. Preserve spendable coins and pending tickets exactly. Credit is a transfer of value already spent, not a cash refund plus a credit. Update the new financial validator to account for converted credit and consumed expansion payments consistently.
4. Keep access preservation separate from credit. Zero-paid legacy access must not automatically become paid ownership of a new room. A partial contribution must not become ownership just because its old purchase ID disappears. Specify the mapping for existing west-wing/Eryops access and placements before implementing the migration.
5. Commit the complete conversion using the existing writer lock and critical-commit mechanism. Retain the validated old snapshot until a successful write; retry the same candidate without rerunning the grant. Test failed write, retry, reload, reset and repeated old/new-schema loads with isolated synthetic storage.

Edge cases to decide/test: full-price receipt versus final-coin interruption; near-complete and simultaneous stand/wing deposits; zero remaining cash with nonzero pending tickets; legacy versus purchased wing; already-placed Eryops requiring preserved space; credit smaller/equal/larger than the target expansion price; carry-forward of surplus; renamed/retired offers; invalid ownership-plus-deposit pairs; grandfathered site access; helpers delivering while the world mapping changes. Do not implement surplus loss, free new-room ownership or cash refunds without a product decision.

## Verification and independent engineering assessment

Executed:

- `node --test tests/save-compatibility.test.ts`: initial sandbox attempt could not start its worker (`spawn EPERM`; no test assertions ran). The authorized elevated rerun passed **45/45**, zero failures/skips.
- `npm test`: passed **221/221**, zero failures/skips, including existing migrations, persistence/session tests and gameplay regressions.
- `npm run build`: passed TypeScript and Vite production build. Vite reports a chunk over 500 kB; bundle splitting is outside this task.

No browser tests or manual browser session were run: this task changes only tests/fixtures/documentation, with no scene, controls or UI changes. Browser storage was never opened or reset. The configured build type-checks `src`, not test files; tests were executed with Node's TypeScript support. All work remains uncommitted.

Verified findings and recommendations, prioritized:

- **High — verified coupling / recommendation:** Historical readers import live `PURCHASES`, `EXHIBITS`, `SITES`, upgrade definitions and coin generation. Legacy museum validation compares its receipt count with `PURCHASES.length`; adding offers can reject an otherwise intact legacy hall. Receipt validation compares to current prices, and economy validation checks current site levels, exact soil keys and recomputed outcomes. Before Phase 7.2 changes these definitions, isolate historical contracts or explicitly migrate them. Do not weaken financial validation to make old saves pass.
- **High — verified representation / recommendation:** The current schema distinguishes paid receipts, partial deposits and zero-paid legacy ownership; no expansion-credit field exists. Introduce an atomic, idempotent transfer with separately specified legacy access mapping before replacing the old wing. The baseline protects the source amounts; it cannot verify an unimplemented destination schema.
- **Medium — verified coverage limit:** These nine fixtures protect all requested states but only four representative historical versions. Existing tests cover more versions; the new corpus does not freeze every historical layout, task-in-progress, fully completed second-site, all-three-ticket-price or migration failure permutation. Add targeted frozen inputs when Phase 7 touches those contracts. Existing helper/task, reset and session tests remain relevant.
- **Medium — verified validator assumptions:** Ticket history has exactly three price buckets, current display-count constraints, a monotonic visit sequence and bounded active visits. Helper validation assumes one available helper. Location and task metadata may normalize independently; financial/progression errors reject the save. Future content/room/helper changes need explicit mapping tests, including the distinction between parsing and load-time recovery.
- **Low — limitation:** This is local consistency validation, not authenticity protection against a deliberately rewritten, internally consistent browser save. Synthetic loader tests also do not prove real-browser durability or child-facing usability. Run isolated browser migration/retry checks when the actual Phase 7 migration is introduced.

Assessment: sufficient as the requested pre-change regression baseline, **not sufficient alone to release Phase 7 migrations**. No production defect requiring a change was exposed by these tests. Before Phase 7.2 alters persisted content, preserve the old validation definitions, decide legacy access/credit destination rules, and add migration tests against these unchanged fixtures. No Critical finding was identified within this bounded review.
