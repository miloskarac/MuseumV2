# Phase 7.4B - Complete room progression rules

Implemented 2026-11-09. The missing pure progression capabilities are complete. Room completion now derives from assembled/restored parts, actual display placement, a matching owned stand and room availability. The former trusted `completedExhibitIds` path has been removed.

This is not a playable-content release. Schema 22, current exhibit completion, purchase commands, west-wing behavior, income, geometry, visitors and navigation are unchanged. No future stand or fossil recipe was added to a production catalog.

## Explicit input contract

All types and queries are in `src/game/permian-rooms.ts`.

```ts
type PermianProgressDefinitions = {
  readonly exhibits: readonly {
    readonly id: PermianExhibitId;
    readonly requiredPartIds: readonly string[];
  }[];
  readonly stands: readonly {
    readonly id: string;
    readonly roomId: PermianRoomId;
    readonly exhibitId: PermianExhibitId;
  }[];
};
type PermianExhibitProgress = {
  readonly id: PermianExhibitId;
  readonly assembledPartIds: readonly string[];
  readonly displayedOnStandId: string | null;
};
type PermianRoomProgress = {
  readonly unlockedRoomIds: readonly PermianRoomId[];
  readonly ownedStandIds: readonly string[];
  readonly exhibits: readonly PermianExhibitProgress[];
};
```

Definitions and progress are separate inputs. Definitions describe the authoritative required parts and which exhibit/room each stand serves. Progress describes assembled/restored parts, the current displayed stand and existing ownership. `null` means the fossil is not displayed. Collected parts do not count as assembled/restored parts. A whole fossil can have a one-part restoration requirement.

These types are projections for pure queries, not new save fields, purchase receipts or a second economy. Tests supply explicitly synthetic recipes and stands for all 17 IDs, including the 14 planned fossils. The production room catalog retains only its Phase 7.4A planning metadata.

Future integration must obtain definitions from approved content and progress from validated game state. The queries check their consistency; they cannot prove the authenticity of arbitrary caller-supplied facts, acquisition history or a payment. They are typed APIs, not raw-JSON/save parsers.

## Functions and signatures

Every progression query now takes three required arguments: `(id: string, progress: PermianRoomProgress, definitions: PermianProgressDefinitions)`.

| Function | ID argument | Result |
| --- | --- | --- |
| `isPermianExhibitDisplayed` | Exhibit ID | `boolean`: assembled/restored and validly displayed |
| `missingPermianRoomExhibits` | Room ID | `PermianExhibitId[] \| undefined`: required exhibits not validly displayed |
| `isPermianFeaturedExhibitDisplayed` | Room ID | `boolean`: the featured exhibit alone is validly displayed |
| `isPermianRoomComplete` | Room ID | `boolean`: available room with every required exhibit validly displayed |
| `permianRoomStatus` | Room ID | `PermianRoomStatus \| undefined`: initial, locked, eligible, unlocked or completed |

`validatePermianRoomDependencies(rooms)` retains its existing signature and implementation. It was not rebuilt or extended in this increment.

All existing callers were in `tests/permian-rooms.test.ts` and now use the new inputs/signatures. There is no legacy overload or optional trusted-completion shortcut. An extra `completedExhibitIds` property cannot influence the queries; a regression test supplies it alongside an incomplete exhibit and confirms that progression stays blocked.

## Display validity

`isPermianExhibitDisplayed` is the shared predicate used by all room-completion, missing-exhibit and featured-exhibit queries. An exhibit counts only when:

1. Its ID exists in the Permian planning definitions and has a room assignment.
2. That assigned room is initially available or explicitly unlocked.
3. Exactly one supplied requirement record and one progress record describe the exhibit.
4. The required-part list is nonempty, contains no empty or duplicate IDs, and every required part appears in `assembledPartIds`.
5. `displayedOnStandId` names a stand, and that stand ID is owned.
6. Exactly one supplied stand definition matches the displayed stand ID.
7. That definition permits this exhibit and assigns the stand to the exhibit's correct room.

A completed/restored fossil without a displayed stand is insufficient. Ownership of an unknown or mismatched stand is insufficient. Moving a stand definition into another room fails even when that other room is also owned.

Duplicate exhibit progress or recipe records and duplicate referenced stand identities fail closed for that exhibit, including identical duplicates: ambiguous data is not arbitrarily selected or merged. Duplicate assembled-part IDs cannot replace a missing part. Duplicate ownership IDs do not add progress. Unrelated records are ignored by the query for the requested exhibit/room.

## Completion, missing exhibits and featured exhibits

Room completion requires availability plus all required displays. The missing-exhibit query returns a fresh array in `requiredExhibitIds` order, irrespective of input ordering. It includes partial/unplaced fossils, missing or invalid stands and exhibits in unavailable rooms. Unknown room IDs return `undefined`, distinct from the empty array for a fully completed known room. Boolean queries return false for unknown IDs; unknown room status is `undefined`.

The featured predicate checks only the room's `featuredExhibitId` through the same validity predicate. It can be true while the room remains incomplete. It never grants ownership, successor eligibility, currency, bonuses, animation state or celebration flags. Tests exercise this independently for Eryops, Moschops and Inostrancevia.

## Ownership versus eligibility

The existing status precedence remains:

1. `completed` when the available room has every required valid display.
2. `initially-available` for incomplete Room 1.
3. `unlocked` when supplied ownership includes an incomplete purchased room.
4. `eligible-for-purchase` when an unowned room's predecessor is complete under the strengthened rules.
5. Otherwise `locked`.

Room 2 therefore requires all four valid Room 1 displays; Room 3 requires all six valid Room 2 displays. Removing any required predecessor stand blocks eligibility. Supplying fossil/stand state for a locked room cannot substitute for owning that room. Conversely, these read-only queries do not revoke an already-owned successor when predecessor completion later becomes absent; purchase authorization belongs to the future transaction system.

Eligibility is available through `permianRoomStatus`, as before. There is no room-purchase command, price/affordability check or persistent ownership update in this phase.

## Independent engineering assessment and Phase 7.5 boundaries

**Verified - Phase 7.4B complete within its pure-rule scope.** All six display conditions participate in completion. Missing and featured queries share the predicate. Invalid assembly/display/ownership combinations tested cannot make an unowned successor eligible. Featured completion alone grants nothing. Dependency checks and planned/live separation remain intact. No Critical defect was identified in this bounded work.

- **High - future integration:** supply authoritative recipe/stand definitions and assemble the projection from validated game state. Do not source definitions or completed/restored-part claims from unvalidated save data. A caller can still lie consistently about ownership; these helpers do not replace a save validator or purchase transaction. There is intentionally no synthetic fallback recipe or stand in production.
- **High - future reachability:** all required exhibits must remain obtainable, reconstructable and displayable without owning a successor room. Room predecessor/display membership validation remains intact, but full excavation progression reachability is still unverified because the future site/acquisition graph does not exist. Test the actual acquisition-to-display paths when those definitions arrive; do not invent unlock conditions here.
- **Medium - persistence and purchases:** future room purchasing must check eligibility and affordability at the transaction boundary, commit ownership atomically and implement an explicit save/legacy-west-wing migration. Room-status queries never perform those operations. Schema 22 must not silently gain planned content or new room fields.
- **Low - integration UX:** unknown room queries deliberately return false/undefined rather than a completed state; the UI must handle unknown separately from an empty missing list. Duplicate relevant records block completion and should be diagnosed by the future validated adapter, not silently merged.

Phase 7.5 still needs the real content/stand mapping, ownership/purchase and persistence integration, acquisition reachability checks, and any approved presentation work. None is implemented or claimed by this pure progression task.
