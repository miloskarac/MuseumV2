# Phase 7.5A — Permian room ownership save contract

## Implemented scope

The application now creates, loads and resets **schema 23** saves. The existing playable museum, three exhibits, prices, purchase eligibility, sites, visitors and geometry are unchanged by this phase. Planned Permian rooms remain inactive gameplay content. In particular, Walchia and the four-exhibit Room 1 completion gate do not participate in live purchases.

## Ownership model

Schema 23 extends the validated schema-22 state with exactly this currently reachable envelope:

```json
{ "rooms": { "version": 1, "owned": [] } }
```

`src/persistence/contracts/rooms-v1.ts` freezes the three stable IDs and initial availability independently of future live content. `permian-room-1` is initially available; `permian-room-2` and `permian-room-3` are not. Room 1 needs no purchase receipt. `ownedPermianRoomIds` and `isPermianRoomOwned` in `src/game/room-ownership.ts` derive ownership from this validated contract, without consulting completion or eligibility. Invalid envelopes fail closed.

The typed future receipt shape reserves `id` (Room 2 or 3), `source: 'purchase'` and `paid`. **No receipt is valid in this version.** The reader accepts only an empty `owned` array, version 1 and exactly the two envelope fields. It rejects unknown or duplicate IDs, free grants, purported paid receipts, completion flags, credits, contributions and unknown fields. No price or affordability rule has been invented. The type describes a future receipt shape; it is not permission to persist receipts today.

Completion remains derived by the isolated Phase 7.4B rules. A synthetic completed Room 1 makes Room 2 eligible in those rules without altering persisted ownership. Neither Room 2 nor Room 3 has a live purchase offer or command.

## Migration and financial preservation

`parseRoomSave` in `src/persistence/room-save.ts` delegates schemas 1–22 through the existing reader chain to a validated schema-22 state, then adds the empty room envelope and changes the top-level version to 23. The historical schema-22 reader and frozen historical contracts retain their meaning.

For schema 23, the reader validates the room envelope, removes it, and validates the remainder using schema-22 accounting. This is correct while room spending is necessarily zero. Unknown root fields, future versions and invalid financial states still fail validation. Readers never write or erase storage; the application persists a migrated candidate through the existing durable committer.

Migration makes no financial adjustment. Spendable coins, pending revenue, lifetime ticket ledger, fossil progress, stand receipts, west-wing receipts, partial contributions, site ownership, helpers, storage custody and upgrades carry forward. Paid west-wing ownership remains a purchase receipt for 18 coins; historical zero-paid ownership remains a legacy receipt. Every reachable partial west-wing contribution from 1 through 17 remains intact. None of these records becomes room ownership or credit.

Parsing retains the previous reader's helper recovery semantics. Loading additionally retires paid visitors and settles deliveries, exactly as the schema-22 loader did; it does not pay tickets again or perform offline work. Tests compare against that established loader rather than claiming that transient delivery/visitor state never changes on reload.

## Runtime integration

- `src/app/prototype.ts` uses the room constructor/loader for startup, restore and reset.
- `src/game/purchases.ts` removes the room envelope when projecting the old economy state and explicitly carries it through schema-23 journey reconstruction.
- `src/game/visitors.ts` dispatches schema-23 ticket payments through the existing ledger path.
- `src/game/storage.ts`, `src/game/upgrades.ts`, `src/game/purchase-payments.ts` and `src/game/cash.ts` accept schema 23 in their existing typed state paths. Their spread-based commands retain the envelope.
- The storage key, save writer, session lock and candidate/commit/retry architecture remain unchanged. Failed critical writes retain the old durable save; retry publishes the frozen candidate once. Reset discards pending work and creates fresh initial ownership.

No second ownership store, mutable completion flag, room purchase transaction, west-wing credit, new content or UI has been introduced.

## Boundaries and next phases

**Phase 7.5B:** define west-wing credit semantics and a versioned migration before altering accounting. Distinguish actual paid receipts, zero-paid legacy ownership and partial contributions; specify one-time conversion and failed-write/retry behavior. This phase intentionally retains all source records and creates no credits.

**Phase 7.5C:** approve room prices, prerequisites, receipt validation and any contribution model. Introduce a versioned save extension with explicit migration; do not reinterpret schema 23 or silently start accepting receipts in its empty-only contract. Financial validation must reconcile room spending and any approved credits alongside existing obligations. Add atomic purchase, insufficient-funds, duplicate-action, retry, reload and reset coverage before enabling UI commands.

Only the currently reachable empty receipt state is verified here. Nonempty future ownership, credits and purchases are not implemented or validated. Full excavation progression reachability also remains unverified: the future site/content graph is not defined. Future acquisition, reconstruction and display prerequisites must be checked for successor-room dependencies and cycles; no new site or unlock rule is implied by this contract.

## Independent engineering assessment

- **Current scope — no Critical or High defect identified.** Verified: strict load validation cannot grant Room 2/3; completion queries do not mutate ownership; migrated snapshots preserve financial and fossil progress; old west-wing receipts and all reachable partial amounts retain their original meaning. Actual transition comparisons and failed-write tests cover the known reconstruction paths.
- **High priority before credits/purchases (future requirement):** extending the receipt type alone is insufficient. Define conversion provenance, one-time credit consumption, full balance reconciliation and atomic transaction behavior in a new version before permitting nonempty receipts. Otherwise credits or spending could be omitted or counted twice. These are integration risks, not features claimed complete here.
- **Medium maintenance risk:** schema-specific reconstruction and type unions require deliberate updates for later save versions. The transition tests detect loss of the current envelope; future fields and nonempty ownership will need their own regression cases. Constructors and the committer trust application-generated candidates; strict validation occurs at the persistence reader, not at every write.
- **Low limitation:** automated browser checks exercise compatibility and recovery, not Luka's enjoyment or every possible user-generated save. No presentation change was made in this phase. The existing bundle-size warning remains.
