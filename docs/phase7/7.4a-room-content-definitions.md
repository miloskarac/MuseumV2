## Definitions and helpers

`src/content/permian-museum.ts` exports:

- `PERMIAN_EXHIBITS`: planning metadata with only `id`, `size` (`large`/`small`) and `implementation` (`implemented`/`planned`). These objects have no parts, discoveries, recipes, art, prices or ownership fields.
- `PermianExhibitId` and `PermianRoomId`: distinct unions for the planning domain. The playable `ExhibitId` union is not expanded.
- `PermianRoomDefinition` and `PERMIAN_ROOMS`: stable ID, Cyrillic display name, ordered exhibit IDs, large/small subsets, predecessor ID, required IDs, featured ID and initial availability.
- `permianExhibitDefinition(id)`, `permianRoomDefinition(id)` and `permianRoomForExhibit(id)`: lookups returning the matching definition, or `undefined` when there is none.

The local `defineRoom` constructor derives large/small subsets from exhibit metadata and uses the ordered membership list as the required set. This avoids separately maintained completion lists for the approved all-exhibits-required rule. Definitions use readonly TypeScript types, consistent with the existing content conventions. They are not a persisted contract and are not imported by historical readers.

`src/game/permian-rooms.ts` exports:

- `PermianRoomProgress`: caller-supplied, readonly `unlockedRoomIds` and `completedExhibitIds`. This is hypothetical input, not a save structure. Completed exhibit IDs mean fully completed displays, not collected fossils, individual parts or deposits.
- `isPermianRoomComplete(id, progress)`: true only when the room is initially available or explicitly unlocked, and every required exhibit ID is completed. Unknown rooms return false. Duplicate IDs cannot replace missing exhibits.
- `permianRoomStatus(id, progress)`: the conceptual status below, or `undefined` for an unknown room.
- `validatePermianRoomDependencies(rooms)`: a pure validator accepting caller-supplied room definitions and returning structured `RoomDependencyIssue` diagnostics. It does not change definitions or enable gameplay.

| Derived status | Meaning |
| --- | --- |
| `initially-available` | Room 1 can be used without a purchase; not yet complete |
| `locked` | The room is not available and its predecessor is not complete |
| `eligible-for-purchase` | The predecessor is complete, but the room is not unlocked |
| `unlocked` | Caller-supplied ownership says the room is purchased/unlocked; not yet complete |
| `completed` | The available room has every required exhibit completed |

Completion takes precedence over availability in this single-status view. Initial availability remains explicit in the definition. Supplied ownership is authoritative: the helper neither revokes it for missing predecessor evidence nor verifies a payment receipt. Supplying completion IDs for an unowned room does not complete that room or make its successor eligible. No helper mutates its input, content, currency or storage, and none calls a purchase action.

For example, completing the four Room 1 exhibits yields `completed / eligible-for-purchase / locked`. Adding Room 2 to the hypothetical unlocked IDs changes only its status to `unlocked`. Completing its six exhibits then makes Room 3 eligible. This example exercises definitions; it is not a live gameplay path yet.

## Required deadlock-prevention constraint

For **every room**, every required exhibit must eventually be obtainable, reconstructable and displayable **without owning any successor room**, including indirect successors. Completion must not depend on ownership of a room whose purchase eligibility already depends on that completion. This applies to the entire dependency path, not just the exhibit's assigned display room.

The new validator checks the dependencies represented today:

- Unique room identities, existing predecessor references, and predecessor cycles (including self-cycles and cycles disconnected from the initial room).
- Consistent roots: an initially available room has no predecessor, and a non-initial room has a predecessor rather than remaining permanently locked under the current status model.
- Each required exhibit has exactly one declared display room. A required exhibit assigned to a direct or indirect successor produces a `successor-exhibit` issue. Requirements using the same room or an ancestor's display do not create this forbidden dependency.

The approved three rooms return no issues. Tests inject self, two-room, three-room and disconnected cycles; missing/duplicate identities; contradictory roots; successor display requirements; and missing/ambiguous display assignments. Validation also accepts frozen inputs without mutation and does not depend on declaration order for validity. An empty diagnostic list means these **declared room dependencies** passed, not that all future progression is reachable.

**Future integration requirement:** when actual site, discovery, reconstruction and stand/access requirements exist, trace every required exhibit through all those prerequisites. A dependency on successor ownership anywhere in obtaining parts, reconstruction or display must block integration, even when the room predecessor graph itself is acyclic. Add tests exercising complete acquisition-to-display paths before enabling room-completion purchase gates. Do not remove required exhibits or assume unknown prerequisites are satisfied to make such tests pass.

No excavation sites, unlock conditions, assembly prerequisites or purchase rules were invented for this validation. The future site/content dependency graph is not defined, so **full excavation progression reachability has not been verified**. Current gameplay, purchase rules and persistence remain unchanged.

## Current integration boundaries

- The new content module has only a **type-only** dependency on the existing `ExhibitId` to check implemented IDs. It does not read or mutate the live catalog at runtime.
- The new game module imports only the new content module. No application, presentation, UI, existing gameplay or persistence module imports either new module. A regression test checks this boundary.
- No new save fields, ownership receipts, room prices, credit rules, site assignments, fossil content or geometry were added.
- All historical contracts from Phase 7.3 remain untouched. Planned exhibit IDs and new room fields remain invalid in schema 22; tests verify that boundary.
- No old save is mapped into this room model. Initially available Room 1 is a definition for future progression, not a migration entitlement or reinterpretation of today's museum.
